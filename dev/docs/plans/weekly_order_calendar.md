# Weekly Special Order + Calendar Skeleton

## Goal

Give each week a pull-based goal: a special order published every Monday that asks for an item carrying a specific clue combination, paying a premium over normal selling. This answers "why am I going on this run" before the run starts, and the calendar skeleton built to schedule it becomes the future home for announced special events (auction previews, intel tip-offs).

## Requirements

1. A Weekly Special Order publishes at the start of each in-game week (weeks are 7-day blocks; day 1 of the campaign is a Monday) and expires unfulfilled at the end of that week's last day — no carryover, no stacking, exactly one order active at a time. Expiry carries no penalty; the weekly cadence absorbs misses.
2. An order is a set of 3+ required clues plus a payout multiplier. An owned item fulfills the order when the player's revealed clue set on that item (revealed surface clues plus hidden clues revealed through Authenticate) covers the required set. The requirement is on *revealed* clues — orders may roll hidden clues, which softly pushes Authenticate usage, but an order whose requirement happens to be coverable without verifying still pays out (soft limit, decided in design conversation).
3. Orders are generated by sampling a real template item, never by free random clue draws — satisfiability is guaranteed by construction, eliminating impossible or mutually exclusive clue combinations without any validation logic.
4. Fulfillment happens through a dedicated turn-in surface in the hub, separate from the nightly customer flow (decided in design conversation). This is a sanctioned second selling channel: the "all selling goes through the unified nightly customer system" rule in the project instructions and the customer-sell system doc must be amended when this ships.
5. A minimal Calendar system underpins the schedule: a data-driven mapping of day index to scheduled events, advanced by the existing day-end flow, with a hub-visible surface showing the current week and upcoming events (initially just the active order and its deadline). The weekly order is the first event producer; irregular special events stay out of scope (see Non-Goals).
6. The active order and its fulfillment state persist across save/load.

## Design

### Order generation (template-item sampling)

At week start, the generator:

1. Builds the eligible item pool: items that can currently appear in lots at locations the player can visit. Sampling from the live pool keeps every order obtainable this week in principle (still subject to lot RNG — the order is a hunting goal, not a guarantee).
2. Picks one template item from the pool, weighted toward items with enough clues to be interesting (an item must carry at least the required clue count to be a valid template).
3. Draws N of the template's clues as the requirement set. Initial tuning: N is 3 or 4, uniform. At most half (rounded up) of the drawn clues may be hidden-type, so Authenticate pressure exists without making every order verify-locked.
4. Sets the payout multiplier from requirement size. Initial tuning: ×1.6 for N = 3, ×1.9 for N = 4 — meaningfully above the conservative sell ×1.2 so the hunt is worth a detour, while the aggressive dice pool can still occasionally beat it.

The order presents the required clues (their display names) and the multiplier; it does not name the template item — the player reasons from clues to likely items, which exercises the same category knowledge the rest of the game builds.

### Fulfillment and payout

The turn-in surface lists the player's owned items that currently satisfy the requirement (revealed clue set ⊇ required set). The player picks one; payout = that item's resolved price (the standard price pipeline result) × the order multiplier, credited as cash. The item is consumed, any research slot on it is cleared, and the usual sell-side knowledge points are awarded. One turn-in completes the order for the week.

Worked example: week 2 publishes an order requiring {blown glass, gilded rim, Moser mark} at ×1.6, sampled from a fine-art vase. The Moser mark is hidden, so the player must win a likely candidate at auction, return home, and Authenticate it to reveal the mark. The verified vase resolves to $900 through the price pipeline; turn-in pays $1,440. Had the player sold it to a conservative nightly customer instead, it would have paid $1,080.

### Calendar skeleton

The calendar is deliberately thin: a schedule (day index → event entries) plus a hub surface rendering the current week. Day-end advances the schedule; week boundaries trigger order expiry then publication. Event entries are data, not behavior — each producer system (today: the weekly order; later: special auctions, intel tip-offs) registers its own entries and reacts to its own dates. Order publication and expiry announce through the global notification system.

## Non-Goals

1. No irregular or one-shot calendar events (special auction announcements, intel tip-offs) — the skeleton only carries the weekly order; the rest stays in the Draft entry "Calendar Special Events".
2. No multiple concurrent orders, order choice, or order rerolls.
3. No new clue or item content authored for orders — generation draws exclusively from existing items and clues.
4. No changes to the nightly customer sell flow, its pricing, or its customer generation.
5. No order-issuer identity (named buyer, faction, reputation hooks) — a future merge with the rival/reputation drafts can add this.

## Acceptance Criteria

1. Every generated order is satisfiable by at least one item in the current eligible pool, by construction, across many generated weeks (no impossible clue combinations ever).
2. A new order appears at the start of each week and an unfulfilled order disappears at the end of it; at no point do two orders coexist.
3. An owned item whose revealed clues cover the requirement can be turned in — including an unverified item when revealed surface clues alone cover it — and pays its pipeline price times the order multiplier; the item leaves storage and sell knowledge points are awarded.
4. An item the player owns that truly carries the required clues but has not revealed them does not appear as eligible.
5. Active order, its deadline, and fulfillment state survive save/load mid-week.
6. The hub calendar surface shows the active order and its deadline; publication and expiry produce a notification.
7. The project-instruction selling rule and the customer-sell system doc are amended to record the order turn-in as the sanctioned second selling channel.
