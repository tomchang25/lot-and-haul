# Registry Standard

Conventions for first-class resource registries in this project. Lot & Haul currently relies on directory-scanned autoload registries for its generated catalog data; new curated content packs may use Catalog Resources instead.

## Choose the pattern

Open a registry when you have a designer-authored `Resource` type backed by `.tres` files and callers need a single source of truth for "does this X exist" or "what are all the Xs". Skip registries for:

- Runtime-only types (no `.tres` backing).
- Resources embedded inside other resources (e.g. `SkillLevelData` inside `SkillData`).
- Small closed sets that belong in constants or enums.

Use a **directory autoload registry** for the current generated catalog shape: many resources of one type, global O(1) by-id lookup, generated output folders, and cross-registry validation.

Use a **Catalog Resource** for curated content packs: authored membership, authored order, alternate test/debug pools, scene-injected content, loot/reward/deck-style sets, or small domains where a folder scan would hide the content list.

If a type meets the bar, the registry is the single source of truth. Don't reconstruct that answer by scanning a different registry.

## Catalog Resources

A Catalog Resource is a `.tres` asset with an exported typed list or other explicit fields pointing at authored content. It owns no runtime state, save data, RNG, or gameplay flow. The system that consumes it receives it explicitly through scene wiring, setup, or another dependency owner.

Required API, when useful for the domain:

- `get_all_<plural>() -> Array[T]` or a domain-specific getter that returns a duplicate.
- `get_by_id(id: StringName) -> T` when by-id lookup is useful.
- `validate() -> bool` for null entries, empty ids, duplicate ids, and domain-specific authored-data problems.

Do not make a Catalog Resource an autoload merely for convenience. If many systems truly need global read-only access later, add a thin database/facade that reads the catalog instead of growing the catalog into a manager.

## File layout

| Thing                 | Location                                                              |
| --------------------- | --------------------------------------------------------------------- |
| Script                | `global/autoloads/registries/<singular>_registry.gd`                  |
| Resource files        | `data/tres/<plural>/`                                                 |
| Path constant         | `DataPaths.<PLURAL>_DIR`                                              |
| Autoload registration | `project.godot`                                                       |
| Audit entry           | own `validate()` + `SaveManager.register_section(self)` in `_ready()` |

Examples today: `car_registry.gd` → `data/tres/cars/`, `location_registry.gd` → `data/tres/locations/`.

If the `.tres` directory is generated by tooling and gitignored, say so in a comment next to the `DataPaths` constant — a fresh checkout without the generator run will hit an empty registry and fail the registry's own `validate()` at boot (driven by `SaveManager.run_validation()`), and that comment is what the next person searches for.

## Required API

Every directory autoload registry exposes, for its resource type `T`:

- `get_<singular>_by_id(id: String) -> T` — O(1) lookup. Returns null on miss. This is the one place null is expected.
- `get_all_<plural>() -> Array[T]` — primary iteration API. Returns resources, not ids.
- `get_all_<singular>_ids() -> Array[String]` — kept for serialization boundaries: save dict keys, config reads, debug prints.
- `size() -> int` — used by the registry's own `validate()`.

**Iterate resources, not ids.** If the next thing a caller does after `for id in get_all_<singular>_ids()` is `get_<singular>_by_id(id)`, they should have iterated resources. The `_ids` form exists for save/load and similar boundaries, not as the default.

**Resource-reference discipline**: see `runtime_type_archetypes.md` § Resource Reference Rule. The short version: outside serialization boundaries, pass Resource refs, not String ids. The same rule extends to `@export var` fields on designer resources and Catalog Resources.

## Forbidden APIs

- **No display-name wrappers.** `get_<singular>_display_name(id)` on the registry is banned. Callers take the resource and read `.display_name`. When the id is missing, crashing is correct — that's a data bug, not a fallback condition.
- **No fallback-to-id accessors.** Any helper of the form "return the resource's field X, or the id if missing" hides data bugs. Same reasoning.
- **No item-scanning inverse lookups.** Scanning `ItemRegistry` to answer a category question (or any registry to answer another registry's question) is the anti-pattern this standard exists to prevent. Use a direct reference or an explicit index, below.

**Exception**: query APIs that take an id as a filter parameter are fine. `ItemRegistry.get_items(rarity, category_id)` is a query, not an index return — the id is an input, not a way to look up a single resource.

## Inverse lookups

When registry A needs to answer "which Bs belong to this A?", prefer in order:

1. **Direct reference on the resource.** If `CategoryData` holds `super_category: SuperCategoryData`, answer via `cat.super_category`. Don't build an id-to-id map.
2. **Index built in `_ready`.** If grouping is needed (e.g. "all categories belonging to this super"), build a `Dictionary` at startup after the dependency registry has loaded.
3. **Never by scanning a third registry.** If the shortest path to an answer is "iterate every item and group them", you're rebuilding a map that should have been a direct field.

### Cross-registry index rules

If your `_ready` builds an index by walking another registry:

- Add `assert(OtherRegistry.size() > 0, "<Self> requires <Other> to load first")` at the top of the index build. This catches `project.godot` ordering mistakes at boot instead of letting them manifest as silently-empty indexes.
- Verify autoload order in `project.godot` — dependent registry listed after the one it reads.
- Typed-array values: initialize with `[] as Array[T]`, not bare `[]`. Return `.duplicate()` from the getter so external mutation can't corrupt the index.

## Cross-registry method naming

When one registry exposes a lookup keyed by **another** registry's id, use the `_for` suffix:

```
CategoryRegistry.get_super_category_for(category_id) -> SuperCategoryData
CategoryRegistry.get_super_category_by_id(super_category_id) -> SuperCategoryData
```

Both methods would otherwise share the signature `(String) -> SuperCategoryData`, and a caller who typed the wrong receiver would get null at runtime with no type error. The `_for` suffix reads as "look up via another id" and makes the mistake impossible to make silently.

Rule: if a method's parameter id-type differs from the registry's own id-type, the name ends in `_for`.

## Checklist for a new registry

1. Decide whether this is a Catalog Resource or a directory autoload registry. Prefer Catalog Resources for curated packs and directory autoload registries for broad generated/global lookup data.
2. For a Catalog Resource: keep it in the owning data domain, export typed content references, expose duplicate-returning getters, and add validation.
3. For a directory autoload registry: script at `global/autoloads/registries/<singular>_registry.gd`, loading via `ResourceDirLoader.load_by_id(DataPaths.<PLURAL>_DIR, id_getter)`.
4. `DataPaths.<PLURAL>_DIR` constant. Comment if gitignored.
5. Autoload line in `project.godot`, placed after `SaveManager`. Check load order if `_ready` reads other registries.
6. Call `SaveManager.register_section(self)` at the end of `_ready()`, and implement `validate() -> bool` (size check + any save-reference checks). Add `migrate()` only if the registry needs to mutate save state at boot.
7. Required API only: `get_<singular>_by_id`, `get_all_<plural>`, `get_all_<singular>_ids`, `size`. Cross-registry helpers use `_for`. No display-name wrappers, no fallback accessors.
8. If the registry builds an inverse index, add the `assert` and confirm load order.

## PR conventions

When a PR touches a registry, include in the description: "Conforms to `docs/standards/registries.md` §<section>". Reviewers check that section. When this standard changes, the PR that changes it audits existing registries against the new rule and fixes or documents deviations in the same PR.
